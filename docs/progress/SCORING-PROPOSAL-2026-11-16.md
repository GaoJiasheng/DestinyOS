# 本命体系「五维」方案：要不要打分、怎么打、先做哪个（2026-11-16）

> 性质：方案文档，未改任何代码。所有数字来自本文 §6 实际跑过的统计（仓库 `8c5adae` 工作区引擎，2000 张随机命盘），脚本放在会话临时目录，没有进仓库。

## 0. 结论摘要

1. **值得做，但不要做成「评分」。**本命盘改叫「命盘侧重 / Chart emphasis」，只表达这张盘里各领域的相对强弱，档位 2–5，不出现 1 档，也不写「x/5」。每一档都能点开看到触发了哪几条规则。
2. **健康维在本命盘里不展示**，只显示事业、财富、感情、人际四维。原因有三：合规上不做疾病预测（`docs/08` §59/§82）；各传统对健康宫的断法分歧最大；这一维出错时代价最高。
3. **试点选紫微斗数。**官禄、财帛、夫妻、交友四宫和四个维度一一对应；需要的盘面事实（主星庙陷、生年四化、六吉六煞、禄存天马）引擎已经全部输出；约 10 条规则就能覆盖。在 2000 张盘上，这套草案的维度之间基本不相关，五维全同只占 1.9%。
4. **八字暂缓，先改喜用神算法。**实测引擎的喜忌是按身强弱一刀切：46% 的盘五行全喜，身强盘官财必喜，身弱盘官财必忌。照传统「官杀→事业、财星→财富」去算，事业、财富、感情三维的相关系数达到 0.69–0.74，结果几乎只是在重复身强还是身弱。
5. **生命灵数和合盘永久不做五维。**灵数没有任何领域对应；合盘本来就有自己的指标（Ashtakoot 36 分制等），不该混进来。
6. 西方占星和吠陀可以排在第三、四期。占星需要先补「本质尊贵」和古典宫主星；吠陀最好的依据是 Ashtakavarga（八分法点数），引擎还没有实现。
7. 规则不写进知识单元的 `scores` 字段，改为每个体系单独一份 `packages/content/<system>/scoring.yaml`，配合 interpret 里的一个盘面视图函数。规则单独设版本号，旧报告不重算。

## 2. 现状（代码事实）

- **分数怎么来的**：`packages/interpret/src/interpret.ts` 约 349–357 行（`DESIGN-GAP: Non-daily base-score formulas are unspecified`），每维 = `config.baseScores?.(chart)`（没配时为 3）+ Σ `retained` 知识单元的 `unit.scores[dim]`，四舍五入后钳到 1–5。
- **`retained` 已经过章节上限截断**：`interpret.ts` 约 150 行，按 `plan.maxUnits` 过滤。如果分数挂在知识单元上，一条单元因为章节满了被挤掉，分数就会跟着变，等于「排版影响分数」。这是本文反对把规则写进 KU `scores` 的主要理由。
- **配置**：`packages/interpret/src/config.ts` 的 `systemConfigs` 中，没有任何体系配置 `baseScores`；`types.ts` 约 49 行定义了 `baseScores?: (chart) => Partial<Record<Dim, number>>`。
- **知识库**：`packages/content/{bazi,ziwei,astrology,vedic,numerology,synastry}/*.yaml` 里 `scores:` 字段一共 0 处。polarity 非 neutral 的只有紫微 70 条、吠陀 68 条，并且全是 `mixed`。字段定义在 `packages/content/src/types.ts:37` 和 `schema/ku.schema.json:61`，`docs/05` 第 31 行写的取值范围是 −3..+3。
- **展示**：`apps/web/components/report/report-utils.ts` 的 `hasScoreSpread`：五项相同就不显示。用到它的地方有 `report-headline.tsx` 约 80 行（雷达图）、`print/print-report.tsx` 约 90 行（印刷版会写「x/5」）、`app/s/[token]/page.tsx` 约 80 行（分享页）、`lib/og-card-render.tsx` 约 56 行（OG 卡）。移动端 `apps/mobile` 只在 dev 页面出现 scores，没有渲染本命分数（按 grep 结果判断）。
- **可借鉴的先例**：每日运势的规则表在 `packages/engine/src/daily/score-rules.ts`（`DAILY_SCORE_RULES`，`focusOf`：官杀→事业、财→财富、食伤→感情、印→健康、比劫→人际），计算在 `scoring.ts` 的 `scoreDaily`（基线 60、钳位 15–95、按阈值映射星级），每维的主要原因输出在 `drivers`。`docs/progress/DAILY-V2.md` 记录了用差异度测试调参的做法（同日五维两两不同 > 55% 等阈值）。本文的校验方法直接沿用这套思路。
- **设计文档的原始设想**：`docs/05-interpretation-engine.md` 约 110 行写「五维评分 = 体系基础分（各体系文档定义）+ Σ KU.scores」，但 `docs/systems/bazi.md`、`ziwei.md`、`astrology.md` 都只在概览章列了「五维评分」，没有定义基础分怎么算。这是设计文档本身留下的空缺。

## 3. 该不该给本命盘打分

### 3.1 四个角度

- **产品定位**：免责声明写的是「娱乐、文化学习与自我反思」（`docs/08` §6.5）。本命盘给出「财富 2/5」读起来像是对一个人一生的定论。每日分数第二天就会变，本命分数不会，所以它的分量远比每日分数重，也更像宿命论。
- **语气规范**：`docs/12` §2 禁止恐吓和绝对化。数字天然就是绝对化的表达，「2/5」不管配什么温和的文案，都会先被读成「差」。
- **合规**：`docs/08` 第 59 行规定「健康章只谈作息与注意，不做疾病预测」，第 82 行规定「不承诺财运」。健康打低分基本就等于疾病暗示；财富打高分又容易被读成承诺。
- **用户预期**：海外华人用户熟悉「紫微看财帛宫」「八字看财星」这类说法。他们想知道「我的盘重在哪」，传统里本来就有「这一宫强、那一宫弱」的说法，所以表达相对强弱有文化基础。他们要的不是分数，而是重点和理由。

### 3.2 选项比较

| 选项 | 好处 | 坏处 |
|---|---|---|
| A 不做（维持隐藏） | 零风险、零工作量 | 概览章少了 PRD 写明的一块（`docs/01` 第 165 行，`docs/02` 第 90 行）；「依据可查」这个卖点在概览层面缺席 |
| B 1–5 绝对评分 | 和每日运势的视觉一致 | 本命低分 = 定论，违背语气规范；分享出去后风险成倍放大；需要回答「为什么我的财富 2 分」这类客诉 |
| **C 命盘侧重（相对档位 2–5，可展开依据）** | 只表达「这张盘里哪方面更有支撑」；每一档都能追溯到具体规则；和传统「宫位强弱」的说法吻合 | 需要新的文案和 UI 标签；需要定切点（Q5） |
| D 只展示最突出的两维 | 最安全，几乎全是正向表达 | 信息量少；不展示弱项会显得像报喜不报忧，依据可查的体验也不完整 |

**建议 C，再加 D 的一句话总结。**具体规则：

- 标题叫「命盘侧重」，不叫「评分」；不显示数字，雷达轴只标档位词：5「突出」、4「有支撑」、3「平稳」、2「多花心思」（en：Standout / Supported / Steady / Takes more care）。
- 最低只到 2 档。最弱的一维文案要写成「这方面更需要方法」，并给出一条可执行的建议，不说「差」。
- 概览句只说前两维：「你的盘面侧重在事业与人际。」
- 健康维不展示（Q2）。
- 印刷版去掉「x/5」；分享页和 OG 卡只带最突出的一维（Q4）。

## 4. 各体系的依据

可靠度分三档：**共识强**（主流教材和各派都这么讲）、**流派分歧**（方向大体一致，细节或取舍因派而异）、**牵强 / 不建议**（要么传统里没有这层对应，要么有合规风险）。凡是写了「需命理顾问复核」的，都是我拿不准、需要专人确认的地方。

### 4.1 紫微斗数（试点，细则见 §8）

| 维度 | 对应宫位 | 依据 | 可靠度 |
|---|---|---|---|
| 事业 | 官禄宫 | 官禄主事业、职位 | 共识强 |
| 财富 | 财帛宫 | 财帛主钱财进出、理财方式 | 共识强 |
| 感情 | 夫妻宫 | 夫妻主婚恋与亲密关系 | 共识强 |
| 人际 | 交友宫（仆役宫） | 主朋友、同事、下属 | 共识强（但「交友宫太强反而夺命宫之势」的「奴欺主」说法属流派分歧，需命理顾问复核） |
| 健康 | 疾厄宫 | 主身体与疾病 | 宫位对应是共识，但星曜在疾厄宫的吉凶判断和其他宫不同（例如七杀守疾厄并不等于身体好），而且直接触碰疾病预测 → **不建议** |

**引擎还缺的东西**：

1. **精细的用神选取**。现在 `packages/engine/src/bazi/analysis.ts` 的 `selectUseGod`（约 85–118 行）：身强就把所有泄耗的五行都当喜，身弱就把所有生扶的五行都当喜，中和的盘如果不需要调候就五行全喜。实测见 §6.2。要打分，至少得做到扶抑、调候、通关三路各选 1–2 个用神，并且分出喜、忌、闲。
2. **十神有没有力**。透干后有没有根、有没有被合住或冲坏，这些都没有输出。
3. **格局成败**。`pattern.notes` 只有「无转化」这类说明，没有成格和破格的判断。

### 4.3 西方占星

| 维度 | 宫位 | 宫位对应的可靠度 |
|---|---|---|
| 事业 | 10 宫（MC）+ 宫主星 | 共识强 |
| 财富 | 2 宫（自有财物）；8 宫是共享资源 | 共识强 |
| 感情 | 7 宫（伴侣）；5 宫是恋爱；金星是感情的主星（karaka） | 共识强 |
| 人际 | 11 宫（朋友、社群） | 共识强 |
| 健康 | 6 宫（日常作息、工作习惯）+ 1 宫（体质） | 宫位对应是共识，但同样有合规风险 → 不建议 |

可以用的因子：宫内有没有吉星（金星、木星）或凶星（火星、土星）；宫主星的本质尊贵（入庙、入旺 / 失势、落陷）；宫主星的相位。**可靠度属于流派分歧**：古典占星（Lilly 等人的尊贵计分体系）有成套的计分法；现代心理占星普遍反对「好宫坏宫」的说法，认为外行星不能用来判吉凶。

需要注意的实测（§6.4）：引擎的 `houses[].ruler` 用的是**现代宫主星**（例如双鱼座归海王星）。在五个目标宫里，70.8% 的盘至少有一宫的现代宫主和古典宫主不同；即使改用古典宫主，56–58% 的宫主星都处在「无尊贵」状态。这意味着尊贵这个因子对大多数盘贡献为 0，区分度主要只能靠宫内有没有行星（核心十颗行星落入率约 51–54%）和相位。引擎还缺本质尊贵表和古典宫主。

### 4.4 吠陀占星

| 维度 | Bhava（宫） | 可靠度 |
|---|---|---|
| 事业 | 10 宫（karma bhava）、10 宫主 | 共识强 |
| 财富 | 2 宫（积蓄）+ 11 宫（收益） | 共识强 |
| 感情 | 7 宫 + 金星（kalatra karaka） | 共识强 |
| 人际 | 11 宫（朋友、人脉、兄姐） | 共识中等（11 宫的核心含义是「收益」） |
| 健康 | 1 宫（身体）+ 6 宫（疾病）+ 8 宫 | 不建议（合规） |

因子和引擎字段（`charts/vedic.ts`）：

- 宫主的尊贵：`bodies[].dignity`，配合 `houses[].lord` 查到对应行星。
- 宫主是否落在 6/8/12 宫（凶宫）或 1/4/7/10、5/9 宫（角宫、三方宫）：用 `bodies[].house` 判断。
- 入宫的吉星、凶星：`houses[].occupants`。注意 6、3、11 宫里的凶星反而算好（upachaya），不能一概减分。
- 焦伤、逆行：`bodies[].combust/retro`。焦伤减分是共识；逆行算吉还是算凶，各派说法不一。
- 瑜伽格局：`yogas[]`。

**最可靠的依据其实是 Ashtakavarga（八分法）的 Sarvashtakavarga 宫位点数**。每宫平均 28 点，高于 28 算强，这是 Parashari 传统里少有的现成量化指标，引擎**还没有实现**。

瑜伽的实测命中率（§6.5）：Raja yoga 56%、Budha-Aditya 52%、Kemadruma 44%。前两个太常见，没有区分度。Kemadruma 是负面格局，引擎用的是简化规则（`packages/engine/src/astrology/yogas.ts` 约 23 行的 DESIGN-GAP 注释：「忽略日与南北交点，也不考虑高级解除条件」），命中率明显偏高，**不能用来计分**，建议另开任务复核这条规则本身。

### 4.5 生命灵数：不适合，建议永久不展示

生命灵数的数字（生命数、生日数、表达数等，见 `charts/numerology.ts`）描述的是性格原型和人生课题，传统里**没有任何「某数主财、某数主事业」的公认对应**。硬把「8 号人」对应到财富，就是在编造依据。个人年、月、日数只有周期含义，也不分领域。结论：直接说不适用，报告结构里不产出这一块。

### 4.6 合盘：不适用，不要混

合盘描述的是两个人的关系，「我的事业」「我的财富」在这里没有意义。现有结构（`charts/synastry.ts`）已经有自己的指标：吠陀 Ashtakoot 八项计分，满分 36（`total`、`kootas`，约 20–44 行）；八字的五行互补度 `elementComplementarity`、喜用互助 `favorableSupport`、配偶星；紫微的命宫、夫妻宫比对；西方的跨盘相位和宫位叠加。这些应该在合盘报告里单独呈现，不要套用五维雷达。

## 5. 统一算法框架

### 5.1 计算形态

```
对每个维度 d：
  raw_d = Σ_rule  [rule 命中] × rule.delta[d]
          — 同一 group 内先求和，再按 group 的 cap 截断（如六吉合计不超过 +0.75）
  raw_d = clamp(raw_d, −2.5, +2.5)
  level_d = cut(raw_d, cutpoints)  →  2 | 3 | 4 | 5
```

- delta 一律取 0.25 的整数倍，存储和计算时乘 4 用整数，避免浮点误差导致同一张盘在不同端算出不同档位。
- 切点 `cutpoints` 来自固定种子的样本（例如 2000 张盘）在 20/50/80 分位上的值，写进 scoring.yaml，并随版本冻结（Q5）。这样档位的含义是「和一般命盘相比」，比「≥ 1.5 就算突出」这种自定的绝对阈值更好解释。
- 不算「总分」。本命盘不需要综合分，算了反而又回到给人打总分的问题。

### 5.2 规则放在哪：`packages/content/<system>/scoring.yaml` + interpret 里的盘面视图函数

| 方案 | 结论 | 理由 |
|---|---|---|
| 知识单元的 `scores` 字段 | 不用 | ① 分数受章节截断和 compactor 影响（§2）；② 一条 KU 的文案触发条件和一条评分规则的触发条件不是一回事，硬绑在一起两边都难改；③ 本命体系有 2700 多条 KU，不可能逐条打分并保持一致 |
| `baseScores` 配置函数（纯代码） | 只用来放「视图」 | 规则如果写在代码里，命理顾问没法审，三语文案也没地方放 |
| **独立 scoring.yaml** | **采用** | 规则是数据：能审、能 diff、能单独设版本；文案模板和规则放在同一行；构建时走现有的 schema 校验和三语产物流程（`packages/content/scripts/build.ts`、`validate.ts`） |

结构草案：

```yaml
# packages/content/ziwei/scoring.yaml
scoringVersion: 1.0.0
dims: [career, wealth, love, social]        # health 不在本命盘展示（Q2）
palaceOf: { career: career, wealth: wealth, love: spouse, social: friends }
clamp: 2.5
cutpoints: [0, 0.75, 1.375]                 # raw < 0 → 2，< 0.75 → 3，< 1.375 → 4，其余 → 5
calibration: { sample: 2000, seed: 20261116, years: 1950-2005, note: "§6 方法" }
groups:
  lucky: { cap: 0.75 }
  malefic: { cap: -0.75 }
rules:
  - id: zw.bright.strong
    scope: target_palace                    # 对每个目标宫各算一次
    when: { path: self.brightnessAvg, gte: 0.75 }
    delta: from_view                        # 取 view 里的数值（亮度均值）
    reliability: consensus
    zh: "{palace}有{stars}，在这里{brightnessLabel}，传统上视为这一领域的底气。"
    en: "{stars} in your {palace} {brightnessLabelEn} — traditionally a steady footing here."
  # ...
```

- **视图函数**（例如 interpret 里的 `ziweiScoringView(chart)`）：把盘面整理成每个目标宫一份易读的事实，比如 `self.majorStars`、`self.brightnessAvg`、`self.mutagens`、`self.lucky[]`、`self.malefic[]`、`opposite.*`，然后规则用现有的 `when` 小语言（`packages/content/src/when.ts` 的 `parsePath`，已经支持 `[key=value]` 过滤和通配）来匹配。视图函数要小、纯、有单元测试。
- **报告结构**：新增 `headline.emphasis`（可选字段），与语言无关：

```ts
emphasis?: {
  version: string;                       // scoringVersion
  dims: Partial<Record<Dim, {
    level: 2 | 3 | 4 | 5;
    raw: number;                         // 0.25 的倍数
    basis: { ruleId: string; delta: number; params: Record<string, string> }[];
  }>>;
  top: Dim[];                            // 最多两维，raw 降序，平局按 dims 顺序
  omitted: Dim[];                        // 例如 ['health']
}
```

  `headline.scores` 保留兼容：有 `emphasis` 的体系把 level 写进去；没有的体系继续是全 3，UI 继续不显示。展示文案由 `ruleId + params` 在渲染时本地化，所以切换语言不需要重算分数。

### 5.3 如何保证同盘同分

- 输入只有 `chart` 和 `scoringVersion`，不读语言、时间、用户 ID，也不读知识单元的选取结果。
- 规则按 `id` 排序后执行；用整数运算（§5.1）；平局按固定的维度顺序处理。
- 测试：A–G 七个出生档案做黄金快照；同一张盘重复计算的结果必须深度相等；zh 和 en 两次 interpret 得到的 `emphasis` 必须完全相同。

### 5.4 如何展示依据（「依据可查」这个卖点）

- 每根雷达轴（或每一维的标签）都可以点开，列出这一维命中的每条规则，例如「+1 巨门在官禄宫（旺）」。规则文案沿用 `docs/05` §4 已有的「依据块」写法，并且能链接到命盘高亮对应的宫位。
- 正向依据排在前面，负向依据排在后面；每条负向依据都要带一句可以执行的建议（见 §8 文案）。
- 底部固定一句话：「侧重来自传统规则的组合，看的是这张盘里各领域的相对重心，不代表结果。」

### 5.5 版本管理

- `scoringVersion` 单独递增：改权重或切点升 minor，加删规则升 minor，只改文案升 patch。每次同时带动 `knowledgeVersion` 升级（`packages/content/version.json`）。
- 报告 JSON 存的就是最终结果（`docs/09` 约 168–172 行：report 已经是最终文本，不再重算），`emphasis` 也连同 `version` 和 `basis` 一起存下来。旧报告的档位和当时的依据始终对得上。
- 旧报告没有 `emphasis`，继续不显示（Q8）。`docs/05` 约 238 行规定「旧报告不自动重算，用户可以点重新生成」，重新生成后才有。
- 切换语言时复用已经存下的 `emphasis`，只重新渲染文案，避免同一份报告的中英文用到不同版本的规则。

## 6. 校验方法与实测统计

### 6.1 样本

用 `packages/engine` 当前源码（经 tsx 运行）生成了 2000 张盘：出生时间在 1950-01-01 到 2005-12-31 之间均匀随机，时分也随机；出生地在北京、广州、台北、香港、纽约、温哥华、悉尼、伦敦八个城市中随机；性别随机；固定种子 20261116；`now` = 2026-11-16。全部算出了八字、紫微、西方占星、吠陀四种盘，失败 0 张，耗时约 79 秒。脚本在会话临时目录，没有进仓库。正式施工时，建议把这套统计改写成 `packages/interpret/test/` 下的分布测试。

### 6.2 八字：现有输出能不能直接打分

| 指标 | 结果 |
|---|---|
| 身强弱 | 中和 53.5% / 身弱 25.4% / 身强 21.1% |
| 喜忌（喜的个数 / 忌的个数） | 五行全喜 46.2% · 2 喜 3 忌 25.4% · 3 喜 2 忌 21.1% · 1 喜 4 忌 7.3% |
| 官杀是不是喜神 | 身强 → 100% 喜；身弱 → 100% 忌；中和 → 占全样本 48.3 个百分点的盘为喜（中和共 53.5） |
| 官杀、财星同喜或同忌 | 96.4% 的盘两者同喜或同忌（只有 3.6% 的中和盘例外） |
| 各类十神「几乎不出现」（加权 < 0.25） | 7.8–9.8% |
| 格局分布 | 10 种格局各占 9–12%，分布均匀 |

我按传统对应关系写了一版八字原型规则：官杀×喜忌→事业，财×喜忌→财富，配偶星+日支→感情，五行均衡+有根+印→健康，比劫+贵人→人际。结果：

- 事业、财富、感情两两相关系数 0.69 / 0.71 / 0.74；健康和人际 0.67。
- 按 1–5 绝对评分映射的话，51.7% 的盘至少有一维 ≤ 2，13.4% 的盘至少有一维是 1。

**结论**：用现有喜忌去算，八字五维实际上只剩「身强弱」一个变量，身弱的人会同时拿到事业、财富、感情三项低分。这既不符合传统（传统讲的是「身弱有印比帮身照样能任财官」），也正是要避免的伤人表达。必须先改用神算法（Q9）。

### 6.6 上线前的校验清单（建议写成测试和人工任务）

1. **分布测试**（自动，固定种子 N = 2000，阈值参考 DAILY-V2）：每维四个档位都要出现，且任何一档不超过 45%；全部维度同档 < 3%；维度两两相关的绝对值 < 0.5（允许的例外要写在 yaml 注释里，如夫官线）；每条规则的命中率在 1%–97% 之间，否则要么说明理由，要么删掉；钳位率 < 5%。
2. **黄金快照**：A–G 七个档案手算一遍并固化（§8.3 是 A 的手算示例）。
3. **极端盘人工复核**：每维取最高和最低各 10 张，交给命理顾问逐张对照传统断语。
4. **断语一致性抽查清单**（紫微，命理顾问逐条确认「方向对」）：
   - 武贪同宫在官禄、化禄或化权 → 事业高档
   - 太阳陷地化忌在官禄 → 事业低档
   - 天府、武曲、太阴庙旺守财帛 → 财富高档
   - 化忌加羊、陀、空、劫在财帛 → 财富低档
   - 禄马交驰在财帛 → 财富加分
   - 夫妻宫空宫借星 → 只取半权
   - 夫妻宫化忌 → 感情偏低档，但文案只说「在意」，不说「不顺」
   - 交友宫左右魁钺 → 人际加分
   - 官禄宫遇火、铃 → 只小幅减分（「激发说」存在分歧）
   - 双主星同宫 → 取平均，不叠加
5. **文案检查**：跑现有的禁用词表（`docs/05` §7）；每条负向规则的文案必须带一个可执行的动作；英文要经过母语级审校（`docs/12` 第 85 行）。
6. **跨体系一致性不作要求，但要提前告知用户**：同一个人的八字原型和紫微试点结果并不一致（A 档案：八字原型人际 −0.875、财富 +0.5；紫微人际 +0.75、财富 −1.0）。侧重模块旁边要有一句「不同体系观察的角度不同」，避免用户以为是 bug。

**为什么先做紫微**：

- 依据最扎实：宫位和维度一一对应，不需要再引入「十神代表什么领域」这一层推理。
- 引擎零改动。
- 规则少，便于顾问一次审完。
- 实测分布健康：维度间不相关，分档均匀。
- 唯一的缺点是紫微需要出生时间，用户覆盖面比八字小。但试点的目的是先把框架、UI 和校验流程跑通，八字等第二期修好用神后直接复用这套框架。

### 8.3 手算结果（与脚本结果一致）

**事业：raw +1.25 → 4「有支撑」**

- +1　Z1：官禄宫有巨门，在这里属旺地。巨门主口才和钻研，传统上视为这一领域的底气。
- +0.5　Z7：对宫夫妻宫的太阳化禄照过来，传统上看作从外部来的助力。
- −0.25　Z6：官禄宫有火星，传统上代表这里节奏更急、起伏更多，稳住步子比求快更重要。

**财富：raw −1.0 → 2「多花心思」**

- 0　Z1：财帛宫的天同在平地，不加分也不减分。这一条只展示，作为说明。
- −1　Z3-忌：生年化忌落在财帛宫（天同化忌），传统上表示你在钱的事情上特别在意、容易反复琢磨。给开销定几条简单规则，会轻松很多。
- −0.25　Z6：财帛宫有擎羊，节奏更急、起伏更多。
- +0.25　Z7：对宫福德宫的太阴化科照过来，有条理上的外部助力。
- 合计 0 − 1 − 0.25 + 0.25 = −1.0。

**感情：raw 0 → 3「平稳」**

- −1　Z1：夫妻宫的太阳落在陷地，不容易施展，更像需要找对方法的地方。
- +1　Z3-禄：生年化禄落在夫妻宫（太阳化禄），传统上表示这里容易遇到资源和顺手的机会。
- 依据里同时出现一正一负、相互抵消，这本身就是很好的「依据可查」示例：用户能看懂为什么是「平稳」。

**人际：raw +0.75 → 4「有支撑」**

- +0.5　Z1：交友宫有廉贞（平）和天相（庙），两颗取平均。
- +0.25　Z4：交友宫有文昌同宫，传统上代表有帮手、有贵人。

**健康（不展示，仅供对照）**：raw +1.75，会落在 5 档（七杀庙 +1、禄存 +0.5、文曲 +0.25）。这恰好说明了为什么不该展示：七杀守疾厄的传统断语并不是「身体好」，单靠通用规则会得出误导性的结论。
